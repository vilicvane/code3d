# OndselSolver WASM 验证

日期：2026-09-05。需求与后续进度：[#21](https://github.com/vilicvane/code3d/issues/21)，
来自 [#9](https://github.com/vilicvane/code3d/issues/9) 的部分约束讨论。

## 结论与范围

C++ → WASM 的技术验证通过。相同 WASM 在 Node 和 Windows 主机 Chrome 的
module Worker 中完成几何约束、欠约束、冗余约束及多对象闭环求解。
可以继续评估将 OndselSolver 作为 code3d 的刚体数值求解后端。

本次没有替换 core 的求解器，没有改变 `on()`、`flip()`、`offset()` 的公共语义，
也没有引入新的装配 API。下文区分实测事实和正式接入建议；接入建议尚非已实现契约。
一次性探针与生成产物不进入正常运行路径。

## 实验环境与构建

- code3d 基线：`43960fa`。
- [FreeCAD/OndselSolver](https://github.com/FreeCAD/OndselSolver/tree/458510ddfd1a96f0afb4a045dc09b57dadd2617c)：
  `458510ddfd1a96f0afb4a045dc09b57dadd2617c`，CMake 项目版本 1.0.1。
- Emscripten 6.0.9；emsdk 仓库版本 `5eb0bde7585670252e8ba05e9d361627bffd08b5`。
- Node 24.18.0，WSL Linux；Windows Chrome 152.0.7977.64，通过 CDP 验证。
- C++17、Release、单线程，静态链接 OndselSolver 至独立的 ES module/WASM。
  上游 C++ 源码无需修改；测试自己的 CMake 直接加入上游 `OndselSolver/` 子目录，
  设置 `ONDSELSOLVER_BUILD_SHARED=OFF`，不构建桌面程序和上游测试程序。
- 上游使用 [LGPL 2.1](https://github.com/FreeCAD/OndselSolver/blob/458510ddfd1a96f0afb4a045dc09b57dadd2617c/LICENSE)。
  本次没有将上游源码或二进制纳入 code3d 发布产物。

编译整个上游库及桥接代码时启用 `-fexceptions`。链接参数为：

```text
-lembind
-fexceptions
-sMODULARIZE=1
-sEXPORT_ES6=1
-sENVIRONMENT=web,worker,node
-sALLOW_MEMORY_GROWTH=1
-sSTACK_SIZE=1048576
-sINCOMING_MODULE_JS_API=['wasmBinary','locateFile','print','printErr']
```

Emscripten 6.0.9 的默认 incoming API 列表不包含 `wasmBinary`。
需要显式加入，否则工厂忽略传入的字节并尝试加载外部文件。
内联 ES module 没有可用于相对路径解析的 URL，还需要提供 `locateFile`。
这两点均已通过浏览器实测确认。

浏览器测试使用具备 HTTP origin 的受控测试文档、module Worker 和内存中的
WASM 字节，不需要启动产品开发服务器，也不依赖跨源隔离或共享内存。
`about:blank` 的 opaque origin 无法在本次 Chrome 环境启动同样的 Blob module
Worker；最小测试确认同一 Worker 代码在 HTTP origin 下可以启动。

## 接口与求解过程

一次调用传入所有刚体的初始位置、四元数、固定标记，以及约束的两端刚体索引和
局部锚点坐标系；一次返回位姿、局部自由度估计和残差。迭代期间没有 JS 回调。

桥接层直接使用 `System`、`Part`、`MarkerFrame` 及以下 joint：

| 几何条件             | 上游类型            |
| -------------------- | ------------------- |
| 两平面共面、法线平行 | `PlanarJoint`       |
| 两直线共线           | `CylindricalJoint`  |
| 点重合               | `SphericalJoint`    |
| 点在线上             | `PointInLineJoint`  |
| 点在平面上           | `PointInPlaneJoint` |

初始化过程按上游 API 执行：为 `Part` 设置位姿和正的质量/惯量，连接局部 marker，
反复执行 `initializeLocally()` / `initializeGlobally()` 直到 `hasChanged` 清除，
随后执行各项 `postInput()` 和 `SystemSolver::runPosIC()`。
没有启动动力学时间积分或借用 ASMT 文件格式。

迭代上限设置为 100，位置迭代容差设为 `1e-10`。
实验残差检查阈值为 `1e-7`；这是本次探针的设置，不是未来产品的统一容差契约。
上游 marker 以局部 Z 作为轴/法线，code3d 锚点使用局部 Y；提取真实锚点的实验
通过在其局部坐标系中附加绕 X 的 −90° 旋转完成转换。

## 验证结果

以下共 20 个案例分别在 Node 与 Chrome Worker 中通过了预期结果检查。
“通过”包括正确拒绝矛盾条件；不代表上游原始成功状态可直接使用。

| 案例                                         | 数量 | 结果                                             |
| -------------------------------------------- | ---: | ------------------------------------------------ |
| 单独面、边、点约束                           |    3 | 可行，分别保留 3、2、3 个局部自由度              |
| 原例边与面组合、交换顺序、从面居中位置初始化 |    3 | 位置 `(5, -15, 0)`，原朝向，沿 Z 保留 1 个自由度 |
| 完全重复的平面条件                           |    1 | 可行，冗余条件不减少自由度                       |
| 相距 1 的两个矛盾平面条件                    |    1 | 补充原始残差检查后拒绝，残差为 1                 |
| 三刚体平面约束链                             |    1 | 可行，共保留 6 个局部自由度                      |
| 尺寸缩放为 0.001、0.1、10、1000 倍           |    4 | 组合约束均可行                                   |
| 固定目标同时平移与旋转                       |    1 | 在目标坐标系中得到一致结果                       |
| 沿自由轴给定初始位移 7                       |    1 | 仍满足硬约束，并保留该自由位移                   |
| 3、10、30 个刚体的闭合点约束链               |    3 | 从扰动位置收敛，各点约束残差小于 `4e-15`         |
| 点面、点线关系                               |    2 | 可行，分别保留 5、4 个局部自由度                 |

闭环测试以圆周上的非共线位置构造刚体与局部连接点，固定第一个刚体，给其他
刚体添加约 0.1 的位置扰动，再求解完整闭环；输入并非预先满足全部约束的位姿。
上游剔除冗余方程后，用 `7 × 刚体数 − 活跃标量方程数` 估计自由度，包含四元数
单位长度方程及固定条件。该数值反映求解位置附近的独立方程情况；奇异构型下
不能当作全局机构自由度证明。

另一次实验直接提取当前 core 创建的两个 Box 的 `edge(3)`、`edge(1)`、`top`、
`bottom` 锚点，而非只使用理想尺寸。结果约为
`(4.9999996, -15.0000004, 0)`，最大原始标量残差约 `4e-8`，同时出现微小旋转。
原因是现有 `top/bottom` 取自带边界余量的包围盒，位置分别为 `10.0000001` 和
`-5.0000001`，而边位于真实几何的 `10` 和 `-5`。这验证了该输入可在实验容差内
求解，也说明正式接入必须统一语义锚点的几何精度。

## 确认的接入难点

### 冗余方程会掩盖矛盾

上游 `PosICNewtonRaphson::run()` 遇到矩阵奇异时移除“冗余”方程。
两个分别要求同一平面处于不同高度的条件，也可能被这一过程处理，最终上游
返回成功，仅留下的条件残差为零。这是实测行为，不能直接转成 code3d 的成功状态。

实验修正是在求解前保存全部原始 `Constraint`，求解后逐一调用
`postPosICIteration()` 更新其表达式与残差，再检查 `aG`，包括已经被替换成
`RedundantConstraint` 的原始条件。只调用 `calcPostDynCorrectorIteration()`
会读取被移除表达式的旧值，错误地拒绝一致的重复约束。

这一处理在重复与矛盾平面测试中均通过，并以 JS 重新计算的几何残差交叉核对。
正式诊断还需要区分“当前候选解未满足条件”“数值迭代未收敛”和有证据的“约束矛盾”；
局部非线性求解失败本身不是全局无解证明。

### 初始位姿影响剩余自由度和分支

上游位置求解带有接近初始位姿的目标，使用质量与惯量构造权重。
单条边关系从模型原点开始，实测得到一个约绕 Z 旋转 90° 的可行解，位置约为
`(-15.0249, -14.9750, 0)`。单条点关系也可能通过旋转减少平移。
因此“有解”不等于符合 code3d 的默认居中、默认朝向。

此外，`PlanarJoint` / `CylindricalJoint` 使用方向余弦方程，允许轴平行或反平行。
它们本身不表达 code3d 所需的正反朝向分支和 `flip()` 语义。
多解选择、可重复的初始位姿、朝向分支及必要的最终方向检查仍需由语义层负责。

### 几何精度需要与求解容差分开处理

原例的包围盒余量不是新的模型尺寸。应为语义明确的 primitive 提供精确锚点，
对拓扑锚点保留其真实几何定义，不能依靠统一放宽容差掩盖锚点不一致。
长度残差与方向残差的量纲不同，正式求解需要分别缩放和检查。

## 正式接入建议

以下是基于本次证据的建议，具体 API 尚待实现时验证：

1. 将数值后端封装为独立、可重新构建和替换的模块，固定上游与工具链版本，
   保留原始条件残差和来源映射；加载方式覆盖普通 Node 与 App 项目运行时。
2. core 将锚点关系编译成几何条件，在组合范围内收集刚体和约束后统一求解。
   硬条件优先；默认居中和朝向只在可行解中参与选择，不能以低权重混入硬条件
   而允许几何误差换取居中。原点、锚点、实例和固定参考的职责需要一起明确。
3. 迁移 `on()`、`flip()`、显式 `offset()`、源码参数追踪和空间工具，替换当前
   “每条约束先确定完整位姿，再比较一致性”的路径。曲线、曲面不自动等同于
   中点切线或采样法线所描述的完整几何重合条件。

本次证明了通用刚体求解后端的可行性；没有验证动力学、碰撞、有限接触区域、
大型装配、所有旋转分支、跨浏览器兼容性或正式发布流程。
