# 交付委派与回报

提交、合并、推送和发布由一个继承完整会话的 subagent 完成交付闭环，包括验证、
冲突处理、远端确认、issue 核验与补关。目标是把交付上下文留在子会话；主 agent
只做必要协调并接收简报。只执行已授权操作；只要求提交不延伸为合并、推送或发布。
单独补查 issue 也按本约定委派，不要求顺带推送。普通开发和与交付无关的只读检查
不因此一律委派。

## 派发

- 调用 `spawn_agent` 时显式使用 `fork_turns: "all"`，保留当前模型与 reasoning
  effort；不截取最近几轮，也不以重新编写的摘要替代完整继承。这样保留共享上下文，
  有利于缓存复用，但不保证实际命中率。
- 派发消息写清实际任务 worktree、主区路径、分支/已知提交、issue、已授权的操作与
  目标（远端分支、发布环境或包版本）、已有验证证据和还需完成的验证。消息是任务
  边界与定位信息，授权依据仍是继承会话中的用户原始指令。
- 普通交付 subagent 继承实际活跃 worktree 和未完成事项，不因自身 fork 另建工作区；
  确需独立隔离时遵循[开始开发](../SKILL.md#开始开发)的例外边界。
- 同一批有依赖的提交、合并、推送和发布交给同一个 subagent 顺序执行。主 agent
  可以继续独立工作，不并发修改交付 worktree、分支或发布目标，也不例行读取
  diff、测试日志、issue 正文和远端状态重做交付核验。执行 subagent 不再递归派发。
- 后续步骤可继续用内部消息或 `followup_task` 交给该 subagent；fork 后的新用户
  指令须及时补充，明确来源和范围，不能假设子线程会自动看到。如果新增授权无法
  直接随用户消息送达子线程，可重新从更新后的主会话以 `all` 派发，在原 subagent
  已结束写操作并回报当前状态后交接，避免仅凭授权转述执行。

## 协调身份与阶段

主 agent 始终保留原任务的协调身份，独占所有协调脚本的写操作，包括心跳、队列、
主区锁、阶段、服务器登记与完成状态。subagent 可以只读查看协调状态，不另行
注册整合 agent，不改写 `CODEX_THREAD_ID` 或 Herdr ID，也不通过冒用主 agent
身份绕过会话校验。执行 Git 和验证不需要改动协调脚本的身份模型。

按 [串行整合流程](../SKILL.md#主-agent-协调串行整合) 交接：

1. subagent 核对范围并在任务 worktree 完成已授权的提交，简报 SHA、验证结论和
   clean 状态。主 agent 据此 `enqueue`/`retry`、`claim`，由脚本固定和校验提交及
   工作区；等待 FIFO 时保留已有开发服务器。
2. 主 agent 取得锁并写入 `merging`，告知 subagent 队列项、精确 commit、
   `base_commit` 和主区路径。subagent 确认实际状态相符后准备合并。
3. subagent 报告合并已准备好；主 agent 写入 `testing` 并确认后，subagent 执行
   最终测试，完成 merge commit 并回报。对完整解决且已验收的需求，最终交付提交
   必须写入 `Closes #编号`，按 [issue 关闭规则](github-issues.md#自动关闭与推送收尾)
   区分完整与部分交付。subagent 核对最终 Git 状态后简报，主 agent 运行 `complete`；
   脚本验证主区 clean 和合并双亲后释放锁，再交接后续已授权的操作。
4. subagent 执行已授权的推送、发布及对应远端/线上验证，按
   [issue 收尾规则](github-issues.md#自动关闭与推送收尾)完成核验、补关和标签清理，
   包括本次推送涉及的其他任务及手动推送后遗留的待收尾记录。核对范围与证据留在
   子会话，完成后给主 agent 简报。主 agent 完成其协调收尾，不再逐项复查 issue。
   仅提交、仅推送、仅发布或单独补查时跳过不涉及的 Git 和协调阶段。

主区锁释放后，主区可能被其他任务推进。推送和发布须核对授权范围及精确提交，
构建与发布使用可追溯到该提交的产物；不要假设稍后的主区 HEAD 或构建目录仍是
刚完成验证的版本。遵循目标项目和平台既有发布流程。

## 意外与恢复

- 在已有授权与任务范围内处理常规冲突和可恢复失败，并保留原因、处理及复验结论。
  需要更改功能或设计时先安全结束当前整合，再回任务 worktree 修复。
- 合并无法继续时，subagent 按串行整合流程恢复、核验并简报；主 agent 据此运行
  `block`，脚本验证恢复状态后释放锁。协调命令拒绝时交回具体错误，由 subagent
  查明原因。subagent 中断或失联时，主 agent 先确认其写操作已停止，再安排恢复
  subagent 检查 Git、队列及进程；不把失联当作已回滚或已完成。
- 推送或发布超时、断线时，先只读确认远端分支、版本或部署状态，再决定是否重试；
  不把命令未返回成功当作外部操作一定失败。仍无法确认时暂停依赖步骤并回报。
- 需要新增授权、扩大范围或无法安全恢复时，通过内部消息尽快通知主 agent，由主
  agent 处理用户沟通。不要为已经继承的有效授权重复请求确认。

## 回报

阶段交接只回报下一步所需的 SHA、状态和动作请求。结束时给出可直接用于用户
答复的简短摘要：完成的操作与提交/版本、验证结论、已关闭 issue 的链接、保留
打开的相关 issue 及原因、工作区状态，以及必要的异常处理或后续动作。
同工作区还有未完成需求时，明确保留其范围和归属，不能只回报本批已提交事项。
没有意外时说明无异常；部分成功需保留区别，例如推送成功但发布失败。

原始日志、完整 diff、逐项 issue 核验过程及大量提交范围留在子会话，必要时附
证据路径供追溯，不整段回灌主会话。主 agent 依据摘要操作协调脚本并向用户报告，
不设置第二轮人工核验；摘要缺项或事实矛盾时让 subagent 定向补查，只有需要用户
决定、扩大授权或处理跨任务冲突时才带回相关细节。
