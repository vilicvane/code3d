# 交付委派与回报

提交、合并、推送和发布由主 agent 派给一个继承完整会话的 subagent，涵盖相应的
最终验证与交付收尾。只执行本次已授权的操作；例如只要求提交时，不延伸为合并、
推送或发布。本约定不要求将普通开发、只读检查也委派出去。

## 派发

- 调用 `spawn_agent` 时显式使用 `fork_turns: "all"`，保留当前模型与 reasoning
  effort；不截取最近几轮，也不以重新编写的摘要替代完整继承。这样保留共享上下文，
  有利于缓存复用，但不保证实际命中率。
- 派发消息写清实际任务 worktree、主区路径、分支/已知提交、issue、已授权的操作与
  目标（远端分支、发布环境或包版本）、已有验证证据和还需完成的验证。消息是任务
  边界与定位信息，授权依据仍是继承会话中的用户原始指令。
- 同一批有依赖的提交、合并、推送和发布交给同一个 subagent 顺序执行，主 agent
  在其运行期间可以做独立的只读核对与交付说明整理，不并发修改交付 worktree、
  分支或发布目标。执行 subagent 不再递归派发交付任务。
- 后续步骤可继续用内部消息或 `followup_task` 交给该 subagent；fork 后的新用户
  指令须及时补充，明确来源和范围，不能假设子线程会自动看到。如果新增授权无法
  直接随用户消息送达子线程，可重新从更新后的主会话以 `all` 派发，在原 subagent
  已结束写操作并回报当前状态后交接，避免仅凭授权转述执行。

## 协调身份与阶段

主 agent 始终保留原任务的协调身份，独占所有协调脚本的写操作，包括心跳、队列、
主区锁、阶段、服务器登记与完成状态。subagent 可以只读查看协调状态，不另行
注册整合 agent，不改写 `CODEX_THREAD_ID` 或 Herdr ID，也不通过冒用主 agent
身份绕过会话校验。执行 Git 和验证不需要改动协调脚本的身份模型。

按 [串行整合流程](../SKILL.md#主-agent-协调串行整合) 交接：

1. subagent 在任务 worktree 完成已授权的提交，回报 SHA、验证和 clean 状态。
   主 agent 核对后才 `enqueue`/`retry`、`claim`；等待 FIFO 时保留已有开发服务器。
2. 主 agent 取得锁并写入 `merging`，告知 subagent 队列项、精确 commit、
   `base_commit` 和主区路径。subagent 确认实际状态相符后准备合并。
3. subagent 报告合并已准备好；主 agent 写入 `testing` 并确认后，subagent 执行
   最终测试，完成 merge commit 并回报。对完整解决且已验收的需求，最终交付提交
   必须写入 `Closes #编号`，按 [issue 关闭规则](github-issues.md#自动关闭与推送收尾)
   区分完整与部分交付。主 agent 核对 Git 状态和提交父节点后 `complete`，再确认
   后续已授权的操作可以继续。
4. subagent 执行推送、发布及对应的远端/线上验证，回报推送前后默认分支 SHA、
   整批新增提交关联的 issue 和关闭关键词，包括本次一并推送的其他任务。主 agent
   根据回报逐项核对当前需求范围和远端包含关系，确认自动关闭或补关并清理状态，
   完成协调收尾。仅提交、仅推送或仅发布的任务跳过不涉及的阶段。

主区锁释放后，主区可能被其他任务推进。推送和发布须核对授权范围及精确提交，
构建与发布使用可追溯到该提交的产物；不要假设稍后的主区 HEAD 或构建目录仍是
刚完成验证的版本。遵循目标项目和平台既有发布流程。

## 意外与恢复

- 在已有授权与任务范围内处理常规冲突和可恢复失败，并保留原因、处理及复验结论。
  需要更改功能或设计时先安全结束当前整合，再回任务 worktree 修复。
- 合并无法继续时，subagent 按串行整合流程恢复主区并报告；由主 agent 核对后
  `block` 释放锁。subagent 中断或失联时，主 agent 先检查实际 Git、队列和进程状态，
  确认没有写操作仍在进行，再安排恢复，不把失联当作已回滚或已完成。
- 推送或发布超时、断线时，先只读确认远端分支、版本或部署状态，再决定是否重试；
  不把命令未返回成功当作外部操作一定失败。仍无法确认时暂停依赖步骤并回报。
- 需要新增授权、扩大范围或无法安全恢复时，通过内部消息尽快通知主 agent，由主
  agent 处理用户沟通。不要为已经继承的有效授权重复请求确认。

## 回报

subagent 在阶段交接、出现阻塞和结束时主动通知主 agent。结束回报须可独立理解，
按实际发生的操作说明：

- **完成情况**：改动概要，提交与 merge SHA、分支、推送远端及已核实的远端 SHA；
  整批关联 issue 的最终提交及关闭关键词，待主 agent 核对的关闭状态；发布目标、
  版本/部署 ID 与可用链接。区分已完成、未执行和结果待确认的步骤。
- **验证**：执行了哪些相关检查、结果及必要证据路径；说明复用的既有验证和本次
  新验证，保留失败后复验的结论，避免只说“全部通过”。
- **意外情况**：遇到的问题、已确认原因或仍待确认之处、采取的处理、复验结果和
  残留影响；没有意外也明确说明。报告部分成功，不把已推送但发布失败合称失败。
- **最终状态与待办**：任务/主区是否 clean、队列/锁与服务器状态、保留的分支和
  worktree，以及还需要主 agent 或用户处理的具体事项。

主 agent 核对关键提交、远端或发布状态及协调状态；已有充分证据时不重复整套
测试。面向用户简述实际结果和有影响的意外，保留必要链接与尚未完成的事项，不
直接转发冗长工具日志。
