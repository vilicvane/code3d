# GitHub Issues 协作约定

仓库：`vilicvane/code3d`。GitHub Issues 是需求状态的唯一来源；`DESIGN.md`、
`TOOLING.md`、`PLAN.md` 和 `plans/` 保留已确认设计、实施方案及历史，关联 issue
但不维护另一份活跃 backlog。`requests/` 是只读历史归档。

## 轻量记录

- 不使用需求模板、固定章节或必填表单。一句话能说明问题就足够；尚无方案或其他
  需要补充的上下文时正文可空。
- 为用户明确提出的独立需求搜索、复用或创建 issue。同一需求的修正和验收反馈写回
  原 issue，不按每轮对话拆单。不把只读咨询或未获认可的建议自动变成开发承诺。
- 按实际需要补充复现、截图、范围、设计链接或验收结论；不要要求用户把已说清楚的
  内容重写成表格。讨论中的方向仍标为讨论，不能因建了 issue 就视为已确认方案。
- `bug`、`enhancement`、`discussion` 区分类型。打开且没有状态标签表示待处理；
  `status:in-progress`、`status:review`、`status:blocked` 三者互斥。
  `status:review` 覆盖等待验收、集成或推送；关闭状态本身表示完成，不另加 done 标签。
- 暂不引入 GitHub Projects、PR 必经流程或自动同步机器人。

## 已确定方案

- 创建 issue 时，把当前已经确定的方案一并写入正文；方案尚未确定时照常记录需求，
  不为补齐正文编造方案。
- 维护当前 issue 时，方案一旦确定或发生实质调整，就及时更新同一 issue 的正文，
  不等到交付时才补记。正文应反映当前采用的方案；重要变更可用评论简述原因和被
  替代的决定，避免读者必须翻遍对话或评论才能知道当前做法。
- 按复杂度概括实现思路、关键决策及理由、范围和约束，必要时补充验证方式。
  简单方案一两句话即可，不强制章节或清单；由 agent 从已有对话和调查结果中整理，
  不要求用户重新填写。详细设计已有仓库文档时，附上链接并保留可独立理解的摘要。
- 已确定方案包括用户已确认的决策，以及 agent 在已授权范围内经调查或验证后
  确定采用的实施方案。候选方向、待验证假设和仍需用户决定的问题必须明确区分，
  不因写入 issue 就成为已确认决策，也不因此扩大需求或执行授权。
- 交付或交接前核对正文与最终采用的方案一致，更新已被替代的描述；相关设计文档
  按各自职责同步，issue 保留当前方案摘要和链接，不另建活跃需求记录。

## 领取与交接

1. 开工前读取 issue 和评论，检查已有工作声明与本地协调状态，避免重复实现。
   开始工作时更新为 `status:in-progress`，简短记录 agent、分支及工作范围。
2. 本地登记 issue URL、worktree、Herdr 会话和独立服务器；心跳和合并锁仅写本地，
   不把每次心跳、工具输出或聊天逐条同步到 GitHub。Issue 标签和评论不能替代原子锁。
   获得合并授权后由主 agent 领取本任务的 FIFO 队首项并管理主区锁，继承完整会话的
   subagent 执行合并和最终测试，主 agent 核对后释放锁；按
   [交付委派与回报](delivery-subagent.md) 交接阶段与结果。不向其他任务会话转发
   合并请求，不把转述的“用户已批准”当作用户授权。
3. 交付验收时改为 `status:review`，记录改动、验证及验收入口。确实受阻时使用
   `status:blocked` 并写明需要的决定；恢复工作时移除旧状态标签。
4. 同一批改动可以关联多个 issue。按下述交付规则，为完整解决且验收通过的需求
   写入关闭关键词；部分完成只引用 `refs #123` 并说明剩余范围。

## GitHub 操作边界

- 使用已认证的 `gh`，明确传 `--repo vilicvane/code3d`；不回显 token。需要授权时
  让用户完成浏览器设备授权，不向用户索取或在仓库内保存凭据。
- 常用读取：`gh issue list --repo vilicvane/code3d --state all --search '<关键词>'`
  和 `gh issue view <编号> --repo vilicvane/code3d --comments`。
- 仅有一句话需求且没有方案或上下文时，可用
  `gh issue create --repo vilicvane/code3d --title '<需求>' --body ''`。
  有已确定方案时随正文写入；多行正文先写入临时文件，再用 `--body-file <文件>`
  创建或更新。标签是 agent 的整理工作，不是提交需求的门槛。
- API 写入超时后先读取确认是否已生效，尤其是创建 issue；不要直接重试产生重复条目。
- 用户批准需求跟踪不等于批准提交、合并、推送、发布、修改仓库可见性或分支保护。
  各自遵循当前任务的授权；也不自动处理无关的外部 issue。

## 自动关闭与推送收尾

- 本地合并与 `coordination.py complete` 不会关闭 issue。`refs #123`、`(#123)`
  也只建立引用。完整解决需求且验收、最终验证通过后，交付 subagent 必须在最终
  交付提交（通常为 merge commit）正文写 `Closes #123`；多个已完成需求各写一行。
  不因尚未获准推送而省略关键词：提交进入远端默认分支时才触发自动关闭。没有推送
  授权时保持 issue 打开，报告“已本地合并，待推送”。
- 推送 subagent 记录并回报推送前后的远端默认分支 SHA，以及整个新增提交范围
  关联的 issue、对应最终提交和关闭关键词；范围包括此前其他任务已本地合并、
  本次一起推送的提交，不能只列当前任务的 issue。
- 主 agent 在推送后逐项读取这些 issue 的当前正文与必要评论，核对完整验收记录及
  最终提交确实已进入远端默认分支；对仍标为“待推送”但提交已在远端的遗留需求也
  补做核对。只在功能分支推送、仍待验收、部分完成或重新打开后还有新增工作时，
  不能仅凭旧的合并记录或状态标签判定完成。
- 已确认完成的需求须核实自动关闭结果，并清理工作状态标签、更新正文中过期的
  “待推送”状态。缺少关闭关键词的既有提交不重写历史；附上最终提交及验证依据后
  手动补关，再读取确认结果。因放弃而关闭要明确原因，不能标成已实现。
- 主 agent 的交付回报包含已关闭的 issue 链接，以及仍打开的相关 issue 和原因。
  已推送但 issue 状态未核对时，收尾尚未完成；该核对不扩大推送或发布授权。

参考：[GitHub 关联与自动关闭规则](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)。
