# code3d prototyping

code3d 的项目代码始终保持在当前认知下可达到的最佳抽象和实现。原型阶段不是积累技术债的理由。

修改三维视口的辅助标记、高亮、关系方向或空间控件时，同时读取 [code3d visualization](../code3d-visualization/SKILL.md)，沿用已确认的尺寸、颜色和几何范围约定。

## Always refactor

- 每次改动都要把所涉及的职责及其真实依赖闭包重构到最佳终态；不能只补症状、绕过错误抽象，或把清理工作留给以后。
- 主路径中不保留已知技术债，包括临时桥接、重复实现、兼容分支、过时入口、死代码、泄漏的内部边界和没有明确外部阻碍的 TODO。
- 现有 API、示例、内部表示和运行时行为都不是天然约束。方向变化时迁移全部相关调用方、测试、示例、文档和工具，然后删除旧语义。
- 不添加 deprecated alias、兼容 wrapper、双轨语义或 fallback，除非用户明确要求，且给出了当前确实存在、无法在本次迁移的外部约束。
- 不以最小 diff、短期开发速度或“只是 prototype”降低结构和实现质量。评价标准是终态是否统一、清楚、完整、可验证。
- “最佳”以当前需求和证据为准，不为假想未来堆叠抽象；但不能以避免扩大当前 diff 为由留下已经确认的结构问题。

## Temporary work

- 只有明确隔离、可丢弃的探索代码、一次性诊断和临时测试探针可以降低长期维护要求。
- 临时代码不能进入公共 API、正常运行路径或持久模型格式，并应在得出结论后删除；只有用户明确要求保留时才能留下。
- 正式单元测试、集成测试、fixture 和测试基础设施属于项目代码，仍必须采用最佳可维护实现，不能借“测试代码”规避重构。
- 如果最佳抽象尚不清楚，先在隔离实验中验证；不要把尚未成立的临时设计接入主路径后再承诺未来清理。

## Semantic values without defensive programming

- 模型对象遵循语义不可变：正常作者 API 中的建模操作产生新值，不能改变旧值已经可观察到的模型语义。
- 语义不可变不要求 `Object.freeze()`、深拷贝或内部完全无 mutation。缓存、trace、惰性计算和 OpenCascade 资源生命周期可以在不改变作者可观察语义时使用 mutation。
- 默认信任项目内类型边界和工具可预见的正常调用方式。不要为正常路径无法触发的误用增加防御性复制、冻结、校验、fallback 或 impossible-state 分支。
- 只有正常作者代码或 GUI/tooling 确实可能产生该状态、错误需要在真实边界被解释，或输入来自明确的不可信外部边界时，才增加校验和恢复逻辑。
- 不得让防御性代码掩盖核心抽象、增加额外心智负担，或被误当成实现正确性的替代品。

## Work from current intent

- 修改核心语义前读取关联 GitHub issue，以及 `DESIGN.md` 和 `PLAN.md` 中相关部分。GitHub Issues 是需求、讨论、验收和进度的唯一跟踪入口；`requests/` 只保留迁移前的历史，不再新增或移动文件来表达需求状态。不能静默改变当前里程碑。
- 一句话说清楚的需求直接作为 issue，不要求模板、固定章节或强制验收清单；agent 创建时记录已有的确定方案，维护时及时同步方案的确定与调整，并按实际需要补充上下文，不把填写工作交给用户。操作 issue 时读取 [GitHub Issues 协作约定](../worktree-development/references/github-issues.md)。
- 区分已确认决策与讨论中的假设。讨论提案、伪代码和候选 API 默认只留在对话中；除非用户明确要求记录或确认，不得将其提升为 `DESIGN.md`、`PLAN.md` 的确定方向或其他规范性文档内容。
- 用户的新设计判断覆盖旧草稿和旧实现。发现两者冲突时先明确冲突，再按新判断重构。
- 修改过程中发现与当前职责直接相关的既有技术债时，将它纳入同一重构；无关区域仍不得借机扩张任务范围。
- 仍须保留用户拥有的工作区改动；“不保留产品兼容性”不等于可以覆盖或删除用户数据。

## Handoff

说明最终保留的唯一语义、完成了哪些必要重构、删除了哪些旧路径，以及仍未决定的设计问题。不能把已知技术债包装成“后续优化”交付。
